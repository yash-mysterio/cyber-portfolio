Building a Detection Pipeline From Scratch

A working SOC workflow built end to end in a home lab — packet capture through to triaged, ATT&CK-mapped alerts, with no SIEM doing the thinking for me. Writing the detections myself is what taught me where they break, which turned out to be the more useful half of the exercise.

00 / Scope

All activity described here was generated and observed on my own isolated lab equipment. The page covers detection and analysis: how attacks were identified, what the detections caught, and where they fail. It is deliberately not an offensive walkthrough, and contains no configuration or instruction for conducting these attacks anywhere.

01 / Why build it

Deploying a SIEM teaches you the SIEM

The standard home lab is a SIEM install with sample data loaded into it. You learn the interface, which is worth something, but the detection logic arrives pre-written and the interesting decisions have already been made by someone else. What counts as a brute-force attempt? Over what window? How many failures before it's an alert rather than a user with a bad morning?

Building from raw capture upward means making those decisions directly. So the pipeline runs from packet capture through detection modules and structured alerting to a classification layer, with the detection thresholds written into the modules themselves — and so every wrong threshold is findable.

02 / The pipeline

Four stages, raw traffic to triaged alert

01

Capture

Packet capture off the lab network into pcap, as the single source of truth for everything downstream.

02

Detect

Python modules parsing captures for behavioural signatures — connection rates, failure patterns, protocol anomalies.

03

Alert

Structured JSON output carrying source IP, packet counts and attack metadata, so alerts are machine-readable rather than log lines.

04

Classify

An AI reasoning layer producing risk score, confidence, and a MITRE ATT&CK technique mapping for each alert.

To generate traffic worth detecting I ran controlled attacks against the lab using Hydra and hping3 — credential brute-forcing, ICMP flooding, and scanning activity. The point wasn't the attacks; it was having ground truth. When you know exactly what you launched and when, a missed detection is unambiguous rather than a maybe.

03 / What it caught

Detections and their ATT&CK mappings

Detection Technique Signal used
SSH brute force T1110 Authentication failure volume and rate from a single source — over 85,000 attempts observed in the heaviest run.
Network service discovery T1046 Connection attempts fanning across ports and hosts from one origin in a short window.
Network denial of service T1498 ICMP volume well beyond baseline, with packet-rate and source concentration as the discriminators.

Mapping to ATT&CK adds more than a label. A detection that fires is a fact; a detection tied to a technique is the beginning of a question — what does this actor usually do next, and am I watching for that too?

04 / What it would miss

85,000 attempts is the easy case

This is the section I'd want to be asked about. Every detection above fires on volume, and volume is the loudest possible version of each attack. A real intrusion is usually quieter than lab traffic by orders of magnitude.

Detections tuned on high-volume traffic catch an attacker who isn't trying to hide. A patient attacker walks straight under their thresholds.

Concretely: password spraying (T1110.003) inverts the pattern my brute-force detection depends on — a handful of attempts against many accounts rather than many against one. Per-source failure counts stay low, so a threshold tuned on high-volume traffic never trips. Catching it needs the aggregation flipped: failures per account across sources, or per source across accounts, over a much longer window.

Similarly, slow scanning defeats a rate-based discovery detection simply by waiting. And a DoS detection keyed to ICMP volume from a concentrated source is the single easiest variant to catch — distributed or application-layer floods look nothing like it.

None of this makes the pipeline useless. It makes it a detection set with a known profile: good against unsophisticated and automated activity, blind to patience. Knowing which is which is the difference between a detection set and a false sense of coverage.

05 / The AI layer, honestly

Where an AI layer helps, and where it doesn't

The classification layer takes each alert and returns a risk score, a confidence level and an ATT&CK mapping. It's the most impressive-sounding part of the build and deserves the most scepticism, so:

  • For attacks the detections already identify, it adds little. If a brute-force module fires, the technique is T1110. A lookup table gets that right every time, faster and for free. Dressing a mapping up as inference isn't an improvement.
  • Confidence scores are only useful if they're validated against outcomes. A confidence number that hasn't been measured is decoration — worse than no number, because it invites trust it hasn't earned.
  • Where it is most defensible is summarisation and context. Turning a cluster of related alerts into a short account of what appears to be happening is real triage work, and it's a more useful direction than the scoring.

It is better to state that plainly than to claim an AI layer is doing more than it is.

06 / Next

Where it goes

  • Rebuild the brute-force detection around per-account aggregation over long windows, then test it against a deliberately slow, low-volume spray to see if it actually holds.
  • Derive thresholds from an observed baseline period of normal traffic rather than from attack traffic alone.
  • Add alert deduplication and correlation — 85,000 attempts should surface as one incident with a count, not as volume in an analyst's queue.
  • Validate the confidence scores against known ground truth, or remove them.
